BUGS FOUND AND FIXED THIS SESSION (all pushed to origin/main)
-----------------------------------------------------------------
Every one of these was caught ONLY by running on real hardware - none
were visible from static review or the Windows dev machine. In order:

  1. image/scripts/*.sh were committed without the executable bit
     (created on Windows, which has no exec-bit concept). Fixed:
     git update-index --chmod=+x. Commit e1251b5.

  2. install.sh ran each service's `pip install -r requirements.txt` from
     the wrong working directory, so the `-e ../../packages/...` editable
     lines inside those files couldn't resolve. Fixed by cd-ing into each
     service directory first. Commit 983b486.

  3. THE BIG ONE: image/systemd/*.service units used
     `Requisite=monstrapro-firstboot.service`. firstboot.service only
     does real work once (ConditionPathExists guard), so on every boot
     after the first, systemd *skips* it rather than marking it active -
     and Requisite= requires the target to be genuinely active. Every
     dependent service (display, worker, agent, portfolio-web, lcd-setup)
     silently refused to start on any boot past the first. Fixed by
     dropping Requisite=, keeping the existing After= (ordering only).
     Commit 568cc9c. Regression test added.

  4. install.sh never ran `pip install -e .` for a service's OWN package
     (only its dependencies via requirements.txt) - every service hit
     ModuleNotFoundError: No module named 'X' the first time it actually
     tried to start (only visible after bug #3 was fixed). Commit
     5d994c5. Regression test added.

  5. lcd-setup.sh's rotation idempotency used one marker file PER
     rotation value (.lcd-rotation-180, .lcd-rotation-0, ...), which
     never got cleaned up - switching 180 -> 0 -> back to 180 silently
     no-op'd on the second 180 because that stale marker was still there
     from the very first install. Replaced with a single
     .lcd-rotation-current file compared against the requested value.
     Commit 251bb10. Regression test added.


FIXED SINCE PAUSING (2026-08-02, later same day, commit 8994bab, pushed)
-----------------------------------------------------------------------
  THE BIG ONE #2: the LCD was stuck showing getty@tty1's own console/login
  shell forever, never the app - despite monstrapro-display.service showing
  active/running with zero crashes the whole time. Confirmed live on real
  hardware, root cause was three compounding bugs:
    1. /etc/monstrapro/env was never created by install.sh at all (nothing
       ever wrote it), so no service ever saw an SDL_VIDEODRIVER override.
    2. Even if it had: this panel (goodtft/MHS35) has no /dev/dri, so
       SDL_VIDEODRIVER=kmsdrm - the original plan, previously set by the
       now-deleted deploy/systemd - can never work here. Tried every real
       SDL driver by hand on the device: all report "not available" except
       the invisible dummy/offscreen ones.
    3. monstrapro wasn't in the `video` group, so it couldn't have opened
       /dev/fb0 (root:video, mode 660) even if a driver had tried to.
  Fix: display now renders off-screen (SDL_VIDEODRIVER=dummy) and writes
  finished frames directly into /dev/fb0 via mmap
  (services/display/src/display/framebuffer.py), auto-sized from the
  framebuffer's own reported 480x320. install.sh now adds monstrapro to the
  video group, creates /etc/monstrapro/env, and masks getty@tty1.service (so
  the console stops fighting the LCD for the same screen). Verified live:
  the app is now visibly rendering on the physical LCD. Rotation was NOT
  re-checked in this pass now that real content is showing - worth a fresh
  look on next resume.

  THE BIG ONE #3 (commit 358803b, pushed): monstrapro-portfolio-web.service
  was crash-looping (Address already in use, port 80) - 560+ restart
  attempts deep by the time this was caught. Root cause: device_agent's
  main() unconditionally bound port 80 for its onboarding setup page
  *before* ever checking whether onboarding was even needed. Found a
  device_agent process that had been alive 45+ minutes, stuck in AP mode
  holding port 80, despite the device having working Wi-Fi the entire
  time - probably wedged from a connectivity race on some earlier
  boot/restart. Fixed: main() now checks has_usable_connection() first and
  returns immediately without touching port 80 when already connected.
  Restarted the stuck process to free the port. Verified live:
  portfolio_web now serves its PIN-gated page at http://monstrapro.local
  (curled it from the Windows dev machine, got the real login page back).
  The PIN itself is on the LCD's footer.

  THE BIG ONE #4 (commit ec85477, pushed): after the LCD fix above, the
  owner noticed the LCD was showing the generic idle screen ("no trades
  yet", "market closed", "never synced") instead of the activation/pairing
  screen, despite the device never having been activated
  (device.activated_at was null the whole time - confirmed by querying
  /var/lib/monstrapro/monstrapro.db directly). Root cause:
  trading_worker.main published `awaiting_activation` exactly ONCE, on
  process entry. display's screen state is rebuilt purely by replaying
  *unconsumed* device_event rows, and consumed_at is one global flag per
  event (not per-consumer) - so once display consumed that single event
  (hours earlier), it was gone forever for any future consumer, including
  a freshly-restarted display process. Restarting monstrapro-display.service
  multiple times tonight (to test the LCD/framebuffer fix) is exactly what
  silently dropped the activation screen back to generic idle - trading_worker
  itself never restarted, so it never got a chance to re-publish.
  Fixed: trading_worker now republishes awaiting_activation on every
  60-second poll instead of once (_wait_for_activation in
  services/trading_worker/src/trading_worker/main.py). Verified live:
  restarted monstrapro-worker.service, the LCD switched to the
  activation/pairing-code screen within seconds.

  NOTE for future sessions: this same one-shot-event-vs-restarted-consumer
  trap could still bite other single-publish events (e.g. wifi_onboarding_started
  if wifi_setup ever needs to survive a display restart mid-onboarding) -
  worth keeping in mind, not fixed everywhere preemptively since only
  awaiting_activation was actually observed to break.
