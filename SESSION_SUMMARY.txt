A CROSS-REPO INTEGRATION GAP FOUND (documented, not fixed)
===============================================================================

While building Track B's bot picker, discovered that each selectable "bot"
on the website is actually a specific (monster identity, algorithm)
variation, e.g. "bellitus_alpha1" or "vectura_draco" — not a bare algorithm
family. But trading_worker's registry lookup only knows the 3 bare engine
slugs (force/aptet/draco).

Fix applied on the NextJS_Monsta side: DeviceBotSelection got a separate
botType field (the engine) alongside botSlug (the specific instance
identity), and both strategy-config/manifest endpoints surface it.

NOT fixed on the Python side yet, because nothing real consumes this data
end-to-end today (NullManifestClient never produces a manifest). Flagged
with detailed comments in:
  - services/updater/src/updater/manifest_client.py (module docstring)
  - services/updater/src/updater/strategy_sync.py (module docstring)
  - services/trading_worker/src/trading_worker/loop.py (module docstring)
Whoever builds the real HTTPManifestClient needs to also fix loop.py to
route via a stored engine field instead of assuming bot_slug IS the engine.

--- B1: device pairing/activation domain ---
Schema (prisma/schema.prisma + hand-written migration — NOT yet applied to
any database; needs `npx prisma migrate deploy` run deliberately):
  - Device model — serial, pairing code (15-min TTL, single-use), bearer
    token (prefix+hash, mirrors the existing ApiKey pattern), userId
    nullable until paired
  - DeviceBotSelection model — botSlug (specific variation), botType
    (engine), params (snapshotted from the registry at selection time)

API routes (src/app/api/devices/):
  - POST /register — unauthenticated, device self-registers, gets a token
    + pairing code once. Refuses to reissue for an already-activated
    device (a serial alone shouldn't be enough to hijack a device).
  - POST /pair — Clerk-authenticated, owner submits the pairing code
  - GET /status — device-token authenticated; what trading_worker's future
    HTTPActivationClient will poll
  - GET /strategy-config — bot selections + Alpaca connection status
    (never credentials)
  - GET /manifest — matches updater's ReleaseManifest contract; artifactUrl
    stays null until a real signed-release pipeline exists
Supporting: deviceAuth.ts (pure token/code helpers), authenticateDevice.ts
(DB-backed auth, DI-testable), a new "device" rate-limit identity kind,
all 4 device-token endpoints registered as public routes (NOT /pair, which
stays Clerk-protected).

--- B2: bot picker UI ---
  - PUT/GET /api/devices/[deviceId]/bot-selection — Clerk-auth + ownership
    checked. Client sends only variation slugs; server always resolves
    botType/params authoritatively from OFFICIAL_BOT_REGISTRY (never
    trusts client-submitted params).
  - /dashboard/devices/[deviceId]/bots — the picker page: up to 10 bots,
    selected ones pinned to top, "Details" opens in a new tab, force/aptet
    /draco engines only (the 3 the Pro Box can run).

--- B3: portfolio preview ---
  - deviceBotPortfolioPreview.ts — blends selected bots' REAL current
    holdings (reusing the same live data path monstra.bot already uses for
    active subscriptions, via a newly-exported computeBlendedStockWeights),
    sector diversity, and a risk/aggressiveness summary from each bot's
    real editorial labels. Equal-weighted across bots (stated explicitly
    in the UI, not left implicit).
  - Deliberately does NOT show fabricated share quantities — a Pro Box's

    against live prices, which nothing server-side can predict in advance.
  - /dashboard/devices/[deviceId]/preview — stat tiles, sector bars, live
    holdings table, back-to-edit / submit.

--- Device management UI (closing the loop) ---
